The first release combines personal deadlines and recurring bills, manually recorded commissions and expenses, an annual business scoreboard, and optional personal progress rewards. It gives the shared scheduler an everyday purpose. It is a product slice of the existing operating platform, not another workflow engine.

## First-release decisions

| Concern | Decision |
| --- | --- |
| Main entrance | Add `/today`, `/planner`, `/business`, and `/goals`; preserve the existing dashboard and its links. |
| Audience | Signed-in individuals using a personal workspace; do not require a self-declared realtor role to manage their own planner. |
| Privacy | Planner, earnings, goals, and progress are private to the individual, even if that person also owns a team workspace. No automatic team-admin access to personal financial records. |
| Scope | USD; calendar year; manually entered receipts/expenses; bills, professional deadlines, appointments, follow-ups, and personal tasks. |
| Recurrence | Once, weekly, monthly, quarterly, annually; explicit local date/time and IANA timezone; occurrence-level completion. |
| Reminders | Persistent in-app reminders first, produced by the existing worker. No claim that reminders send email, push, SMS, or pay bills. |
| Earnings | Recorded cash received less recorded business costs, labeled **before taxes**. Pending commissions remain separate. |
| Input modes | Gross commission with itemized withheld deductions, or actual net deposit. Never deduct broker fees again from a net deposit. |
| Progress | Optional private goals/milestones and weekly habits; no leaderboard, monetary reward, or points for sending messages. |
| Jamie | Read the authorized personal summary and propose structured changes for confirmation through the same APIs used by forms. |
| Existing work | Link to the shortlist, sprints, and workspace review queue. Do not count an intake answer or a completed task as a closing. |

## What the user sees

`Today` opens with an earnings card and three short sections: **Coming up**, **Needs your attention**, and **Your progress**. Quick actions are **Add deadline**, **Record income**, **Record expense**, and **Ask Jamie**. Show useful empty states instead of invented demo totals.

`Planner` defaults to an agenda, with a month view as an alternative. Each row shows the subject, due date, amount when applicable, status, and the next available action. A bill has **Record payment**; a task has **Mark complete**; a reminder has **Snooze** or **Dismiss reminder**. Those actions must remain distinct.

`Business` shows recorded net, recorded deposits, known gross commissions, known withheld deductions, paid expenses, pending income, and upcoming bills. Put the formula and the underlying entries one click away. If some receipts are net-only, say gross/deduction totals are incomplete; an unentered gross amount is not zero.

`Goals` shows annual net-income or closing-count targets and completed weekly reviews. Progress can decrease after corrections, and celebrations can be disabled. Spatial growth is an optional decoration driven by real progress, never a prerequisite for using the planner.

The UI uses **deadline**, **payment**, **income**, **review**, and **progress**. Job IDs, leases, connector health, and evidence hashes stay in operational screens.

## RP1 — Domain contracts, calendar rules, and money calculations

Deliverable: pure functions and schemas with meaningful behavior tests. No database or provider required.

### New `lib/realtor-workspace/contracts.ts` — write in this order

1. Import `z` and the existing timezone validator; export `currencySchema = z.literal('USD')`.
2. Define strict UUID, bounded title (1–160), note (0–2,000), local `YYYY-MM-DD`, and local `HH:mm` schemas. Validate real calendar dates, not just regex shape.
3. Define `plannerItemKindSchema`: `bill`, `professional_deadline`, `appointment`, `follow_up`, `task`, `weekly_review`.
4. Define a strict recurrence discriminated union: `once`; `weekly` with interval 1–52; `monthly` with interval 1 or 3; `yearly` with interval 1–10. Store original anchor date and optional inclusive end date. Quarterly is monthly interval 3.
5. Define `dueSpecSchema`: local date, nullable local time (date-only item), timezone, recurrence, and up to three distinct reminder offsets in calendar days, each 0–365. Date-only reminders default to 09:00 local; show this in preview.
6. Define item input: kind, title, notes, due specification, nullable `expectedAmountCents` for bills only, and optional typed property reference. Property reference must pass existing domain authorization before persistence; defer other resource types.
7. Define occurrence mutations: `complete`, `reopen`, `skip`, `reschedule`, `record_payment`; require `expectedRevision` and `requestKey`. `record_payment` includes actual payment amount and paid date. No `paid: true` shortcut.
8. Define reminder mutations separately: `dismiss` or `snooze` with future timestamp. Never overload an occurrence completion action.
9. Define `commissionInputSchema` as `gross` or `net_deposit`. Gross mode requires positive gross cents and bounded deduction rows (`broker_split`, `transaction_fee`, `other_withheld`); net mode requires a positive deposited amount and forbids deduction rows.
10. Define `expenseInputSchema` with amount, paid date, category, payee label, and note. Categories include broker dues, MLS, association, education, license, insurance, marketing, software, and other. No tax-deductibility classification.
11. Define expected-income input with estimated take-home cents, expected date, label, and optional authorized property reference. It is never treated as received income.
12. Define goal input (`net_income`, `closings`, `weekly_reviews`), positive target, year, revision, and request key. Define preferences for timezone, reminders enabled, gamification enabled, celebration enabled, hide amounts on Today, and nullable user-reported records-start date. This coverage date is a disclosure, not proof the entries are complete.
13. Export inferred input/output types. Every mutation schema is `.strict()` and excludes actor/owner, computed totals, job lease, reward amounts, and role fields.

### New `lib/realtor-workspace/money.ts` — statement-level implementation

14. Set a bounded per-entry limit, e.g. `MAX_MONEY_CENTS = 1_000_000_000_000`, and reject fractional, unsafe, negative, non-finite, or out-of-range cent inputs. Deductions may be zero; receipts/expenses must be positive.
15. Export `parseUsdToCents(text)`: trim; require a plain decimal string with at most two decimal digits; split dollars/fraction; pad fraction; build integer cents without `parseFloat(text) * 100`; enforce the limit.
16. Export `normalizeCommission(input)`: gross mode sums deductions, rejects deductions above gross, returns `grossCents`, `withheldCents`, `receivedCents = gross - withheld`, and `grossKnown: true`.
17. In net mode, return `receivedCents = deposit`, `grossCents: null`, `withheldCents: null`, `grossKnown: false`. Do not back-solve a supposed broker split.
18. Export `calculateRecordedNet(receipts, expenses)` for fixtures/client previews using safe integer arithmetic or bigint. Server annual aggregation uses PostgreSQL exact arithmetic, not a paginated browser list.
19. Return `knownGrossCents`, `knownWithheldCents`, `receivedCents`, `paidExpensesCents`, `recordedNetCents`, `netOnlyReceiptCount`, and `grossComplete`; `recordedNet = received - paidExpenses`.
20. Represent aggregate cents as decimal integer strings in API responses to avoid bigint/JSON rounding. Keep formatting helpers explicit about USD and negative values.
21. Support optional broker percentage only as a form calculator: user enters basis points, round once to nearest cent with a documented half-up rule, preview the fixed deduction, and persist the cents actually confirmed. No automatic broker-cap accounting in v1.

### New `lib/realtor-workspace/recurrence.ts`

22. Export `expandOccurrences(spec, from, until, limit)`, preserving the original anchor rather than adding months to the previous clamped date.
23. Monthly January 31 yields February's last day and then March 31. Annual February 29 yields February 28 in non-leap years and February 29 when it exists again. Surface this rule in the recurrence preview.
24. Treat weekly repetition as local calendar weeks, never as a fixed UTC millisecond interval. Store date-only due dates as dates; do not turn them into UTC midnight display values.
25. Expose a narrow tested wall-clock-to-UTC helper from `schedulerPolicy.ts` if needed; preserve its current earlier-instant overlap and forward-shift gap behavior. Tests must prove existing scheduler behavior stays unchanged.

27. Export `buildOccurrenceKey(itemId, originalLocalDate)`. Rescheduling one occurrence retains this identity and changes its effective date; it does not generate a second completion/payment opportunity.
28. Bound materialization to 90 days and 200 occurrences per item, with at least the next occurrence even when it lies beyond the horizon. Return a continuation/horizon marker; never silently truncate a successful result.
29. Series edits affect only pending occurrences from a chosen effective date. Completed/paid history keeps its old title/date/version snapshot. Skips affect one occurrence; archiving a series stops future reminders.
